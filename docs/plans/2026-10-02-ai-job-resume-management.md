## 一、目标与首版范围

面向校招、社招求职者，交付可部署的多用户内测产品，完成：

**导入真实经历 → 添加岗位截图或描述 → 生成岗位专属简历 → 编辑导出 → 跟踪投递与面试。**

已确定的产品取舍：

- 中文优先，桌面浏览器完成简历编辑，手机支持录入岗位、查看进度。
- 用户自备 API Key；未配置时仍可手动管理岗位、编辑和导出简历。
- 截图支持视觉模型识别，并内置 OCR 兜底。
- PDF、DOCX 都纳入交付，默认推荐 PDF。
- 首版采用邀请注册，不做支付、自动海投、招聘网站爬虫、机构协作和独立运营后台。

**复用范围：**已核查的上游代码已有投递管理、JD 提取、匹配评分、简历版本和 BYOK。现有岗位定制只修改个人简介，本项目重点扩展到完整经历选择与改写，不重复建设已有模块。

依据：[现有 AI 实现](https://github.com/reactive-resume/reactive-resume/blob/b53c43c3722741946603ac46beda173931aeb646/packages/api/src/features/applications/ai.ts)。本计划依据源码和文档制定，尚未部署实测。

## 二、技术与项目约定

### 固定底座

以已核查的上游提交 `b53c43c3722741946603ac46beda173931aeb646` 为开发基线，版本标识为 `5.3.2`，保留 MIT 许可证及版权声明。

沿用 React、TanStack Router、Hono、oRPC、PostgreSQL、Drizzle、Better Auth 和现有简历渲染体系。Node.js、pnpm 版本以该提交的配置为准，核查时分别为 Node.js 24、pnpm 12.6.0。

依据：[上游配置](https://github.com/reactive-resume/reactive-resume/blob/b53c43c3722741946603ac46beda173931aeb646/package.json)。

### 开发前先建立规范

1. 先建立 `AGENTS.md`，写明目录职责、隐私约束、验证命令、部署入口和禁止自动 push。本次计划落盘已建立初始规范。
2. 引入上游时合并其工程规范，保留工作区包边界，不覆盖本地规范。
3. 沿用上游目录结构：前端按功能组织，业务逻辑进入现有 API 功能包，数据与迁移归数据库包，渲染复用 PDF/DOCX 包。
4. 文档进入 `docs`，开发脚本进入 `tooling`；上传原件、导出文件和临时产物不进入 Git。临时处理文件完成即清理，异常遗留文件 24 小时内清理。
5. 上游更新人工评估后合入，首版开发期间不自动跟随 `main`。

### 运行方式

- Docker Compose 单机部署，包含应用、后台 worker、PostgreSQL、Redis及持久文件卷。
- 新增 BullMQ 处理 OCR、AI 定制和投递文件生成；数据库保存任务状态，队列只传任务 ID。
- OCR 使用 Tesseract 5，内置简体中文和英文模型，采用独立进程处理，避免阻塞 Web 服务。
- 保留上游存储抽象；内测默认私有本地文件卷，不额外引入对象存储服务。
- 用户密钥沿用服务端加密保存机制，数据库、Redis、日志和前端响应不得出现明文 Key；加密主密钥通过运行环境注入。

参考：[Tesseract 官方仓库](https://github.com/tesseract-ocr/tesseract)、[BullMQ 任务 ID 与去重限制](https://docs.bullmq.io/guide/jobs/job-ids)。

### P1：多用户内测入口与 AI 配置

- [ ] 主导航收敛为“我的经历、岗位、简历、设置”；复用现有登录体系。
- [ ] 新增一次性邀请机制，通过管理员 CLI 生成邀请，不建设管理后台。
- [ ] BYOK 设置提供服务商、模型、Key 和高级自定义地址，支持连接测试。
- [ ] 首批验收覆盖 DeepSeek 文字模型及一个支持图片的 OpenAI-compatible 接口；其他上游适配器保留，但不宣称全部通过验证。
- [ ] 文本能力与图片能力分别探测，修改模型、Key 或地址后重新测试。
- [ ] Key 无效、余额不足、限流和网络失败分别给出可操作提示，用户返回设置后保留原任务输入。
- [ ] 服务器禁止自定义模型地址访问本机、内网及云元数据地址，覆盖重定向与实际连接目标校验。

**交付标准：**两个用户的岗位、简历、文件和 Key 完全隔离；只配文字模型也能通过 OCR 使用截图入口。

### P2：真实经历库

- [ ] 每位用户建立一份主经历档案，复用现有简历编辑组件，支持教育、实习、工作、项目、技能和奖项。
- [ ] 支持导入 PDF、DOCX及手动填写。PDF 无文本层时复用 OCR；解析失败保留原件，允许手动补充。
- [ ] 导入结果先供用户校正，确认后生成事实版本。每条经历保留稳定 ID、来源和版本。
- [ ] 定制简历读取已确认的版本；AI 不得反向修改主经历档案。
- [ ] 校招默认突出教育、项目和实习，社招默认突出工作经历与成果，用户可调整排序。

**输入边界：**简历文件不超过 10 MB；PDF 不超过 10 页；DOCX 设置解压后体积上限，拒绝异常压缩文件。

**交付标准：**导入、校正、保存和再次编辑完整可用；修改经历后产生新版本，历史生成记录仍能找到原始依据。

### P3：岗位截图与描述导入

- [ ] 在现有岗位模块增加统一输入区，支持粘贴文字、粘贴图片和上传图片。
- [ ] 单次导入一个岗位，最多 5 张 PNG/JPEG/WebP，每张不超过 10 MB、解码后不超过 20 MP；长图分片识别，重叠区域去重。
- [ ] 已通过图片测试的模型优先识别；不支持图片或识别失败时转入本地 OCR，再交给文字模型解析。
- [ ] 保存原始截图、原始文本和结构化结果，提取公司、岗位、地点、薪资、职责、要求、招聘类型、毕业届别和截止日期。
- [ ] 原文没写的信息保持为空；含糊内容标记待核对，不能由模型补齐。
- [ ] 用户在同一页确认岗位信息后，可直接“保存并生成简历”；缺少基础配置时引导补齐，输入不丢失。
- [ ] 同用户重复岗位提示复用，不自动合并或覆盖。

**交付标准：**文字、普通截图、多图和长图均可进入岗位记录；没有 Key 时仍能 OCR 提取文本并手动保存岗位。

### P4：岗位专属简历生成

生成流程固定为：

**岗位要求分析 → 选择相关事实 → 调整排序与表达 → 校验事实 → 展示差异 → 用户接受 → 创建独立简历。**

- [ ] 输出覆盖个人简介、技能展示、项目、实习与工作经历，不限于改写简介。
- [ ] 每项建议关联事实 ID 与事实版本；展示选用原因、改写前后内容和待补充信息。
- [ ] 公司、学校、学历、时间和业绩数字不能被模型修改；没有依据的职责、技能和成果不得作为可接受建议。
- [ ] 服务端校验结构、引用和受保护字段。语义核对与用户审阅共同降低编造风险，不把“引用了 ID”视为真实性证明。
- [ ] 不满足岗位的条件进入“差距提示”，不能自动写进简历；匹配结果不宣传为招聘系统通过率。
- [ ] 接受建议后创建新简历，沿用原编辑器和模板；原始经历与其他岗位简历不变。
- [ ] 旧的“只改简介”功能从主流程退出，保留兼容接口但明确其能力，避免两种定制入口混淆。

**任务可靠性：**

- [ ] 创建时固定经历版本、JD 版本和 AI 配置版本；输入变更后，旧提案标记过期，重新生成后才能接受。
- [ ] 每用户同时执行一个生成任务；刷新、关闭页面后可恢复查看。
- [ ] 数据库唯一请求标识与事务保证一次接受只创建一份简历；不能仅依赖队列去重。
- [ ] 仅对明确的临时错误有限重试；Key 撤销、配置变化和内容校验失败不自动重试。
- [ ] 模型调用超时后无法保证对方未计费，不进行无提示的重复调用。

**交付标准：**生成的是可编辑的完整岗位简历；差异可审阅、依据可追溯，重复点击不产生重复简历。

### P5：投递闭环与部署交付

- [ ] 复用岗位列表、看板和时间线，提供待投递、已投递、笔试、面试、Offer、结束状态，保留上游已有状态的兼容映射。
- [ ] 支持截止日期、面试时间、跟进日期和备注；首版只做站内到期提示。
- [ ] 标记已投递时，冻结所选简历的数据及导出文件；如实际投出的是外部文件，允许上传该文件作为记录。
- [ ] 投递快照独立保存，不依赖删除简历时会级联清理的普通版本表。
- [ ] 文件必须由同一份冻结数据生成；生成失败明确显示失败，不能提供指向当前可编辑简历的替代下载。
- [ ] 删除工作简历不删除历史投递；删除岗位或注销账号时，按用户操作清理对应历史与文件。
- [ ] 提供部署、迁移、备份、恢复、邀请管理命令和内测说明。部署前备份数据库与文件，回滚覆盖数据库兼容性，不能仅回退镜像。

**交付标准：**从全新 Docker 环境完成安装和恢复；历史投递文件可下载，Key 可正常解密，能继续生成新简历。

## 四、数据与接口变更

沿用 oRPC 与现有简历数据结构，避免再建立一套简历格式。

| 对象 | 最小新增内容 |
|---|---|
| 主经历档案与版本 | 用户归属、确认版本、事实条目及来源引用 |
| 岗位扩展 | 招聘类型、毕业届别、截止日期、JD 版本、原始素材关联 |
| 生成任务与提案 | 输入版本、模型配置版本、任务状态、差异、事实引用、失败原因 |
| 投递快照 | 冻结简历数据、导出文件、投递时间；独立于工作简历生命周期 |
| 邀请 | 一次性凭证摘要、有效期和使用记录 |

新增接口按能力分组：

- `profile`：获取、保存、导入、确认经历版本。
- `applications.importSource`：提交岗位文字或图片，返回识别任务。
- `tailoring.create/get/accept`：发起定制、查看提案、幂等接受。
- `tasks.get/retry`：恢复进度与显式重试。
- `applications.recordSubmission`：冻结投递内容并记录文件。
- `aiProviders`：扩展文字与图片能力检测。

所有接口从登录态取得用户身份；文件、任务和关联资源也必须单独校验归属。新字段采用增量迁移，旧简历继续可编辑、可导出；已有投递不会被伪造为具备历史快照。

## 五、验收、交付与默认约束

### 自动化验证

执行上游适用的检查：

```text
pnpm typecheck
pnpm test
pnpm build
pnpm test:e2e
pnpm exec turbo boundaries
```

新增代码运行只读 Biome 检查；上游 `pnpm check` 会改写文件，不能当作只读验证命令。

重点回归：

- [ ] 跨账号读取、修改、下载、重试任务和关联简历全部被拒绝。
- [ ] JD 提示注入、虚构经历、篡改数字，以及“引用真实 ID 但正文编造职责”被覆盖。
- [ ] 生成期间修改经历/JD、撤销 Key、服务重启、任务超时、重复接受均有明确结果。
- [ ] 导出期间编辑或删除简历，不改变投递文件内容。
- [ ] 普通中文、英文混排、长项目描述、多页简历的 PDF/DOCX 无乱码、截断和重叠。
- [ ] 数据库、原件、导出文件及解密所需配置完成一次全新环境恢复验证。

### 真实样本验收

使用授权或脱敏的 10 份简历，校招、社招各 5 份；20 份岗位材料，其中至少 10 份为截图。

- [ ] 清晰截图中已明确出现的关键字段，人工对照准确率目标不低于 90%；缺失信息不得编造。
- [ ] 10 份定制简历逐份核对受保护事实，不能出现新增学历、公司、时间和业绩数字。
- [ ] 至少完成一条真实文字模型流程、一条视觉模型流程及一条 OCR 兜底流程。
- [ ] PDF/DOCX 下载后人工打开检查，不能只以接口成功或文件存在作为通过。
- [ ] 无真实 Key、样本或 Docker 环境时，对应项目标为未验证，不能用 Mock 替代验收。

### 最终交付

交付代码、项目规范、环境示例、迁移、部署与备份脚本、验收记录及已知限制。记录导入成功率、生成成功率、接受率、导出失败率和任务耗时，日志不记录简历正文与密钥。

本次只落盘项目规范与开发计划，不开始 P0 或后续开发，不自动 push，不自动部署到公网。正式内测邮件服务与真实模型凭据作为外部配置项，缺失时保留明确的验收缺口。
