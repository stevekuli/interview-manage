### 环境适配（偏离上游默认之处）

1. **宿主机 5432 被本机 PostgreSQL 16 Windows 服务占用**（端口冲突，不动用户本机服务）。新增 `tooling/compose.dev.win.yml`，将 postgres 容器映射到 `127.0.0.1:5433`：
   `docker compose -f compose.dev.yml -f tooling/compose.dev.win.yml up -d postgres redis`，`DATABASE_URL` 指向 `localhost:5433`。
2. **git `core.autocrlf` 必须为 `false`**：默认 `true` 会把全仓检出为 CRLF，导致 tooling 包对 committed 生成物（GitHub workflow、semantic-css 参考文档）的逐字节断言失败。已重置检出为 LF。
3. **Node 版本必须 ≥ 24.9.0**（详见"修复 2"）。

## 二、代码修复（阻碍首版的两项 + 一项测试兼容）

### 修复 1：`apps/server/tsdown.config.ts` — Windows 路径被误判为第三方外部依赖

- 现象：`pnpm build` 的 server 产物只有 1KB 桩文件，`node dist/index.mjs` 报 `ERR_MODULE_NOT_FOUND`（导入 `D:\...\startup\checks.ts`）。
- 根因：`shouldExternalizeThirdParty` 用 `id.startsWith("/")` 识别"已解析的绝对路径"；Windows 上解析结果为盘符开头（`D:\...`），不匹配任何分支 → 被当作 neverBundle 外部化 → 全部相对导入与 workspace 包（`@reactive-resume/env/server` 等）以裸 `.ts` 源路径 import 形式留在产物里。上游 CI 仅跑 Linux，未暴露。
- 修复：改用 `node:path` 的 `isAbsolute`（Windows 上识别盘符路径）。修复后产物 2.02MB 完整 bundle，服务器正常启动。

### 修复 2：Node v24.0.2 → v24.9.0（环境，非代码）

- 现象：服务端公开简历 PDF 渲染稳定 500，日志 `EMFILE: too many open files`（libuv 层，进程 OS 句柄仅 271，8189 上限远未到）；`packages/pdf` 41 个测试文件、`tooling` 集成测试同样 EMFILE；`packages/ui` 测试 worker 启动崩溃。
- 定位：独立进程 `import('@react-pdf/renderer')` 正常；换 Node v24.9.0（仍满足上游 `engines: "24.x"` 与 `.nvmrc` 的 24）后：pdf 包 82 文件/1038 用例全过、ui 352/352、tooling 109/109、服务端 PDF 渲染恢复。结论：Node 24.0.2（24.x 首批 patch）在 Windows 上的 fs/loader 回归。
- 操作：`nvm install 24`（24.9.0），服务器以 `D:\Development_environment\nvm\v24.9.0\node.exe` 启动。**后续所有构建/测试统一用 24.9.0。**

### 修复 3：`packages/resume/src/stylesheet/selector.esm.test.ts` — Windows 下 spawn pnpm 失败

- 根因：`spawnSync("pnpm", ...)` 无 shell 时 Windows 解析不到 `pnpm.cmd`（status: null）；开 shell 后 cmd 又破坏 `-e` 的引号。
- 修复：Windows 下带 shell 并把 import 脚本改走 stdin（`input: "import(...)"`），Linux 行为不变。

## 四、运行注意（本地约定，已同步 AGENTS.md）

1. 基础设施：`docker compose -f compose.dev.yml -f tooling/compose.dev.win.yml up -d postgres redis`（postgres 宿主端口 5433）。
2. 服务器（生产模式验证）：`NODE_ENV=production PORT=3000 node apps/server/dist/index.mjs`（用 Node 24.9.0；`packages/env` 自动读根目录 `.env`）。
3. **跑单元测试前临时移走根目录 `.env`**：`packages/env/src/server.ts` 会 `process.loadEnvFile(.env)`，测试进程会连上真实 Redis，`view-dedup`/rate-limit 类测试因共享 Redis 状态互相污染而失败（上游 CI 无 `.env` 文件故不触发）。验证完恢复。
4. e2e：`DATABASE_URL=... pnpm exec playwright test --workers=2`。高并行（默认 workers）在本机偶发资源饿死超时。
5. `pnpm check` 会改写文件（Biome `--write --unsafe`），只读检查用 `pnpm exec biome check <path>`。
